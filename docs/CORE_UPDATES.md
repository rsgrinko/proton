# Обновление проектов на Proton

Проекты на Proton — не composer-зависимость, а копия `framework/` в момент
старта. Дальше ядро живёт своей жизнью, а у проекта — своя. Этот документ —
про то, как затянуть в проект новые правки ядра, не потеряв своё и не гадая,
что вообще изменилось. `docs/UPDATING.md` — практическая шпаргалка по шагам,
здесь — почему устроено именно так.

## Правило: framework/ проект не патчит

Всё, что можно решить снаружи `framework/` — решается снаружи. Если решения
нет — значит, в ядре не хватает точки расширения, и её стоит завести, а не
лезть в файл ядра руками. Иначе следующее обновление либо затирает патч, либо
требует ручного слияния файла, который вообще не должен был меняться.

Два готовых механизма:

**События.** `Events::fire('http.responded', [...])` в `Kernel::handle()` —
единственное место, куда стоит цеплять что угодно, что должно случаться после
каждого ответа. `mail.sending` в `Mail::send()` — то же самое для писем,
слушатель получает объект `Message` и может его поправить (лишний заголовок,
своя подпись) до отправки. Подписка — `config/events.php` проекта, ядро не
трогается. Полный список событий и когда каждое стреляет — `config/events.php`.

**Слоты каркаса.** `View::fillSlot('layout.head', '<style>...</style>')` в
`bootstrap.php`/`config/services.php` проекта — разметка попадёт в
`<?= View::slot('layout.head') ?>` внутри `framework/View/views/layouts/main.php`,
а сам файл каркаса проект не копирует и не трогает. Слоты на сегодня —
`layout.head` (перед `</head>`) и `layout.topbar` (в шапке, рядом с
«Уведомления»). Не хватает точки — новый слот заводится в самом ядре одной
строкой `View::slot('имя')`, это не патч поверх чужого решения, а расширение
самого механизма. Подробности — `docs/ROUTING.md`, раздел «Шаблоны».

Для полной замены каркаса (не расширение, а другая раскладка целиком) слоты
не подходят — там как и раньше, `resources/views/layouts/main.php` перекрывает
файл ядра одноимённым. Это осознанный компромисс: проект перестаёт получать
обновления этого файла автоматически, зато ничем не ограничен в разметке.

## Версия ядра — мажор.минор.патч, бампается руками

`framework/VERSION` — обычный текстовый файл, `1.4.2`. Не хук на каждый
коммит — версия ядра размечает не коммиты, а точки, к которым имеет смысл
синхронизировать другой проект, и это решение человека, а не скрипта:

```
php bin/proton core:bump              # патч: 1.4.2 → 1.4.3
php bin/proton core:bump minor        # 1.4.2 → 1.5.0 (что-то серьёзное, новое)
php bin/proton core:bump major --breaking --note="Права: view/manage вместо одного на раздел"
```

Команда одним махом правит `VERSION` и дописывает запись в
`docs/CHANGELOG.md` — оба места иначе легко разъезжаются, если делать руками
по отдельности. `--breaking` помечает запись `**Ломает:**` — сигнал, что
синхронизация не бесплатна, нужно будет что-то доделать руками на стороне
проекта (пример — переназначение прав ролям после перехода на `view`/`manage`).

Бамп — отдельный маленький коммит после того, как фича или фикс, трогающие
`framework/` или формат конфига, закончены, а не по ходу работы: смотреть на
весь диф целиком и решать «это мажор» точнее, чем гадать по каждому коммиту
на пути к нему.

## `Core\Updater` — сравнение по контрольным суммам, не по git-истории

Раньше единственный способ понять, «что из ядра проект уже патчил», — читать
git log с начала проекта и диффать всё руками (см. историю `docs/UPDATING.md` —
именно так собирался список расхождений при живом переносе). Контрольные суммы
переносят эту работу на компьютер:

```
php bin/proton core:check --baseline
```

Разово (сразу после того, как проект завели от ядра, или один раз сейчас —
задним числом, для того, что уже есть) — хеширует всё в `framework/` и
сохраняет как доверенное состояние в `framework/.checksums.json`. Дальше:

```
php bin/proton core:check
```

Пересчитывает суммы и сравнивает с сохранёнными — без похода к ядру вообще,
чистая локальная проверка «ничего не поправили в обход правила с последнего
раза». Полезно гонять и просто по расписанию/в CI, не только перед переносом.

```
php bin/proton core:diff --path=../proton
```

Три списка — не два, потому что «менялось у нас» и «менялось в ядре» это два
независимых булевых значения, а не одна ось:

- **безопасно взять** — изменилось в ядре, не менялось у проекта с последнего
  `core:check --baseline` — файл просто копируется;
- **требует ручного слияния** — изменилось и там, и там — единственный
  случай, где действительно нужны глаза, а не автоматика;
- **ядро больше не содержит** — сверяется с `app/`, `config/`, `routes/`,
  `resources/views/`: если файл или символ (`Класс::КОНСТАНТА`,
  `Класс::метод(`) нигде не используется — можно удалить; если используется —
  выводится, где именно, вместо того чтобы удалить вслепую или промолчать.

```
php bin/proton core:sync --path=../proton --apply
```

Копирует только первый список, обновляет `VERSION` и `.checksums.json` под
новую базу. Без `--apply` — тот же отчёт, что у `core:diff`, ничего не
пишется: цена ошибки здесь выше, чем у `migrate` (та хотя бы откатывается),
поэтому по умолчанию — только план, не выполнение.

Статический разбор ссылок в `app/`/`config`/`routes`/`resources/views` ловит
не всё. Он видит `Класс::член` — так находится и пропавший файл целиком
(по `use`/инстанцированию — `new Класс()`, подсказке типа), и пропавший
именно этот статический член. А вот `(new Класс())->метод()` — обычный вызов
метода объекта — не отслеживается вовсе: не отличить по тексту, какому
классу принадлежит `$viewer` или `$user`, чтобы проверить его метод. Скрытую
зависимость нового файла ядра от другого файла ядра (сегодняшний пример —
`history.php` зовёт `AuditEntry::badge()`, а не наоборот) статикой тоже не
поймать — это ловится только реальным прогоном:

```
php bin/proton core:sync --path=../proton --apply
php bin/proton test
```

Тесты остаются последним и самым надёжным словом — они реально грузят классы
и реально падают с точным местом ошибки, а не гадают по тексту.

## `core:latest` — версия и changelog ядра с GitHub, без клонирования

```
php bin/proton core:latest
```

Два обычных `GET`-запроса через `Support\HttpClient` (никакого нового HTTP-кода,
никакой авторизации): `framework/VERSION` и `docs/CHANGELOG.md` с
`raw.githubusercontent.com/<repo>/<ветка>/...` — файлы отдаются напрямую,
без похода в API и без лимита в 60 запросов/час (это ограничение только у
`api.github.com`). Адрес репозитория и ветка — `PROTON_CORE_REPO`,
`PROTON_CORE_BRANCH` в `.env`, свои у каждого проекта (gitea, зеркало на
GitHub — что удобнее).

`core:diff --remote`/`core:sync --remote --apply` — та же идея, но нужно
содержимое всех файлов, не только `VERSION`: команда качает архив веткой
одним запросом (`.../archive/refs/heads/<ветка>.tar.gz`), распаковывает
`PharData` (входит в PHP, ничего доустанавливать не нужно) во временный
каталог и дальше работает с ним как с обычным `--path`. Ни `git`, ни сеть
внутри самого приложения при обычной работе не участвуют — только когда эту
команду вызвали явно.

Ничего из этого не бегает само: ни по расписанию, ни на каждый запрос —
только когда разработчик сам вызвал команду.
