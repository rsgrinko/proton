# Перенос обновлений ядра в свой проект

Свой проект на Proton — не composer-зависимость, а копия `framework/` в
момент старта: `git clone`, дальше своим репозиторием. Ядро продолжает жить
и меняться само по себе, и рано или поздно захочется затянуть его новые
правки, не потеряв то, что накопилось поверх своего.

Автоматического обновления нет: composer тут нарочно не участвует. Но
сравнение и большая часть переноса — команды `core:*` (`docs/CORE_UPDATES.md` —
почему устроено именно так), а не ручной `diff` по всему дереву.

## Что переносится, а что — нет

- `framework/` — переносится, и по правилу проекта ничего своего в нём быть
  не должно вовсе (см. «Точки расширения» в `docs/CORE_UPDATES.md`): что
  нельзя решить снаружи — решается новым событием или слотом в самом ядре,
  а не патчем поверх чужого файла.
- `config/*.php`, `routes/*.php`, `resources/views/*` (кроме
  `layouts/main.php`, если он не переопределён своим) — свои решения
  проекта: набор прав, пунктов меню, разделов. Ядро может поменять *формат*
  записи (например, добавить новый ключ в элемент конфига) — это стоит
  перенять; содержимое конфига — что именно в нём перечислено — решает сам
  проект.
- `app/`, `migrations/` — целиком свои, из ядра сюда ничего не льётся
  напрямую (переносится схема, не файл — см. шаг 3).

## Разово при старте проекта

```bash
php bin/proton core:check --baseline                           # свежий клон, framework/ не трогали
php bin/proton core:check --baseline --path=../proton-1.0.0    # проект постарше, с правками в framework/
```

База — суммы ядра, от которого проект отсчитывается. Свежему клону подходит
свой `framework/`, он и есть ядро. Если в `framework/` уже есть свои правки,
база берётся от ядра той версии, от которой заведён проект: иначе правки
станут невидимы и будут затёрты при следующем обновлении этих файлов.
Почему так — `docs/CORE_UPDATES.md`, «База — это ядро».

Проект, заведённый на ядре 1.0.0, первый раз переносится через `--path`:
в 1.0.0 `--remote` не работал, а база там — снимок своего `framework/`.
Сначала перенести `framework/Core/Updater.php` и `framework/Console/`
(команды `core:*`), затем заново завести базу с `--path`.

## Шаг 1 — план обновления

```bash
php bin/proton core:diff --path=../proton
# или, без соседнего клона на диске:
php bin/proton core:diff --remote
```

Три списка: что можно взять безопасно (в ядре изменилось, у себя не
трогали), что требует ручного слияния (изменилось и там, и там), что ядро
больше не содержит — с проверкой, ссылается ли на это ещё `app/`, `config/`,
`routes/`, `resources/views/` прежде чем предлагать удалить. Отдельным
разделом — ссылки в своём коде, которые могут сломаться после переноса
(`Класс::метод`, которого в новой версии уже нет).

`--remote` без `--path` качает архив ветки из `PROTON_CORE_REPO`/
`PROTON_CORE_BRANCH` (`.env`) одним запросом — ни `git`, ни клонирование не
нужны.

## Шаг 2 — применить безопасную часть

```bash
php bin/proton core:sync --path=../proton --apply
```

Без `--apply` — тот же план, что у `core:diff`, ничего не пишется. Копирует
только «безопасный» список, файлы из «ручного слияния» не трогает —
смотрите diff апстрима по каждому и переносите нужный кусок сами, старая
правка остаётся на месте нетронутой. Слитый файл отмечается разобранным:

```bash
php bin/proton core:resolve framework/Support/Csv.php --path=../proton
```

Пока в ручном слиянии что-то есть, `framework/VERSION` остаётся старым;
версию ядра он получает на последнем `core:resolve` (или сразу на
`sync --apply`, если сливать было нечего).

Список «может сломаться» статикой ловит не всё — скрытую зависимость нового
файла ядра от другого файла ядра (не вашего кода) видно только реальным
прогоном:

```bash
php bin/proton test
```

## Шаг 3 — конфиги и миграции переносить руками, не копией

Изменение *формата* конфига (пример: у пункта меню в `config/menu.php`
появился ключ `group`) стоит перенять — иначе код ядра увидит в массиве
конфига дыру. Изменение *содержимого* (какие права, разделы, пункты меню у
проекта) остаётся решением проекта — `core:sync` конфиги не трогает вовсе.

Миграция ядра переносится файлом с новым таймстампом, а не файл-в-файл: тот
же таймстамп, что в апстриме, почти наверняка уже занят своей миграцией в
проекте, и получится коллизия. Содержимое (что делает `up()`/`down()`) —
как в апстриме, дата в имени файла — своя, отражающая момент переноса:

```
migrations/20260918100000_add_user_theme.php   ← своя дата, не дата коммита в ядре
```

## Шаг 4 — после переноса

```bash
php bin/proton test        # весь набор, не --filter по переносимому куску
php bin/proton status
php bin/proton worker:restart   # если очередь/расписание тоже задело перенос
```

Коммитить самому и не одним махом: перенос — это чужой код, зашедший в свой
репозиторий, его стоит прочитать перед коммитом, а не доверять автоматике.
