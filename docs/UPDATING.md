# Перенос обновлений ядра в свой проект

Свой проект на Proton — не composer-зависимость, а копия `framework/` в
момент старта: `git clone`, дальше своим репозиторием. Ядро продолжает жить
и меняться само по себе, и рано или поздно захочется затянуть его новые
правки, не потеряв то, что накопилось поверх своего — свои патчи ядра
(бывают, хоть их и стараются избегать), свои `config/*.php`, свои разделы
вместо демо-«Заметок».

Автоматического обновления нет и не будет: composer тут нарочно не участвует,
значит и `composer update` тоже. Перенос — ручная, но небольшая при
регулярном повторении операция.

## Что переносится, а что — нет

- `framework/` — переносится, но не файлом на файл целиком: часть файлов
  свой проект мог уже подправить под себя (см. шаг 2).
- `config/*.php`, `routes/*.php`, `resources/views/*` (кроме
  `layouts/main.php`, если он не переопределён своим) — свои решения
  проекта: набор прав, пунктов меню, разделов. Ядро может поменять *формат*
  записи (например, добавить новый ключ в элемент конфига) — это стоит
  перенять, раз новый формат ожидает шаблон или код ядра; а вот содержимое
  конфига — что именно в нём перечислено — решает сам проект.
- `app/`, `migrations/` — целиком свои, из ядра сюда ничего не льётся
  напрямую (см. миграции ниже — переносится схема, не файл).
- `docs/*.md` в своём проекте — свои копии документации ядра. Перенося
  задокументированную функцию, стоит поправить и описывающий её абзац,
  иначе доки разойдутся с кодом в первый же день.

## Шаг 1 — найти, что в ядре реально изменилось

Если исходники ядра и своего проекта лежат на одной машине (два рабочих
каталога), сравнение — обычный `diff`. Единственная ловушка на Windows:
ядро может быть в CRLF, свой проект — в LF (или наоборот), и голый `diff`
покажет отличия там, где их на самом деле нет. Сравнивать нужно с
`tr -d '\r'`:

```bash
CORE="/путь/к/proton"
diff -rq --strip-trailing-cr "$CORE/framework" framework | grep -v "^Only in"
```

Для конкретного файла из списка — что именно изменилось:

```bash
diff <(tr -d '\r' < "$CORE/framework/Http/Kernel.php") <(tr -d '\r' < framework/Http/Kernel.php)
```

Если исходников ядра рядом нет — тот же список получается по коммитам
между версией, с которой начинали (или на которой остановились в прошлый
раз), и текущей `HEAD` апстрима.

## Шаг 2 — узнать, что из ядра уже своё

Прежде чем тащить чужую правку в файл ядра, стоит проверить, не правили ли
его в своём проекте, — иначе перенос молча затрёт свою правку:

```bash
git log --oneline --follow -- framework/Http/Kernel.php
git diff <коммит, с которого начинали>..HEAD -- framework/
```

Свои правки прямо в `framework/` — редкость и обычно временная мера: то, что
прижилось и оказалось общим местом, со временем перекочёвывает и в само
ядро (тогда при следующем переносе можно смело брать версию апстрима вместо
мержа) — но проверять стоит каждый раз заново, а не полагаться на память о
том, что было в прошлый раз.

## Шаг 3 — тащить файл-в-файл, а не весь framework/ разом

Файл ядра без своих правок — просто копия (`tr -d '\r'`, чтобы не занести
CRLF в LF-репозиторий, если он на LF):

```bash
tr -d '\r' < "$CORE/framework/Http/Router.php" > framework/Http/Router.php
```

Файл со своей правкой — ручной мёрж: смотрите diff апстрима, переносите
новый кусок, свою правку оставляете на месте.

Опасность здесь реальная, не теоретическая: копия одного файла может молча
тянуть за собой чужую зависимость — новый метод в шаблоне или новый вызов в
скопированном файле, которого нет в модели или сервисе, если сам метод не
перенесён вместе с ним. Единственный надёжный способ поймать такое — прогнать
тесты сразу после переноса каждого куска, а не оптом в самом конце:

```bash
php bin/proton test
```

## Шаг 4 — конфиги и миграции переносить руками, не копией

Изменение *формата* конфига (пример: у пункта меню в `config/menu.php`
появился новый ключ, который стал понимать шаблон меню) стоит перенять —
иначе новый код ядра увидит в массиве конфига дыру. Изменение *содержимого*
(какие права, разделы, пункты меню у проекта) остаётся решением проекта.

Миграция ядра переносится файлом с новым таймстампом, а не файл-в-файл: тот
же таймстамп, что в апстриме, почти наверняка уже занят своей миграцией в
проекте, и получится коллизия. Содержимое (что делает `up()`/`down()`) —
как в апстриме, дата в имени файла — своя, отражающая момент переноса:

```
migrations/20260918100000_add_user_theme.php   ← своя дата, не дата коммита в ядре
```

## Шаг 5 — после переноса

```bash
php bin/proton test        # весь набор, не --filter по переносимому куску
php bin/proton status
php bin/proton worker:restart   # если очередь/расписание тоже задело перенос
```

Коммитить самому и не одним махом: перенос — это чужой код, зашедший в свой
репозиторий, его стоит прочитать перед коммитом, а не доверять автоматике.
