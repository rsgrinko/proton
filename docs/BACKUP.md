# Резервные копии базы

Копия делается средствами самой базы, складывается сжатой в `var/backups` и
сразу проверяется. Негодный файл не сохраняется: лучше знать, что копии нет, чем
думать, что она есть.

Внешних утилит не нужно — ни `mysqldump`, ни `gzip`. Их может не оказаться, а
`exec()` на хостинге часто закрыт.

## Команды

```bash
php bin/proton backup:create            # сделать копию, проверить, убрать лишние
php bin/proton backup:create --keep=14  # и оставить больше копий, чем обычно
php bin/proton backup:list              # что лежит в каталоге
php bin/proton backup:list --check      # то же, но каждую копию ещё и проверить
php bin/proton backup:restore <файл> --force   # заменить данные копией
```

В панели раздел **Копии** (право `system.manage`): сделать, скачать, проверить,
удалить. Восстановления в браузере нет нарочно — замена всех данных делается
осознанно, из консоли.

## Как делается копия

**SQLite** — `VACUUM INTO`: база сама пишет согласованную копию, не останавливая
работу. Дальше файл сжимается, имя получается вида
`proton-2026-09-13-031500-a7Kd-sqlite.sqlite.gz`.

**MySQL** — обычные запросы: структура из `SHOW CREATE TABLE`, данные порциями по
500 строк, значения экранирует сам драйвер. Дамп сразу пишется в `.sql.gz`, в
конце — маркер, по которому видно, что файл не обрезан.

Случайные четыре символа в имени нужны не для красоты: две копии в одну секунду
(так бывает — перед восстановлением делается страховочная) иначе получили бы одно
имя, и вторая затёрла бы первую.

## Проверка

Сразу после создания файл открывается заново:

- SQLite — `PRAGMA integrity_check` плюс пересчёт таблиц: в копии их должно быть
  больше нуля;
- дамп MySQL — разбор текста: сколько `CREATE TABLE` и дошёл ли файл до маркера.

Не прошло — файл удаляется, а команда или панель говорят, почему. Ту же проверку
можно повторить когда угодно: `backup:list --check` или кнопка «Проверить».

Проверка SQLite разжимает копию во временный файл `var/tmp/backup-check-*.sqlite`
и убирает его за собой сразу же — но на Windows PDO не всегда отпускает файл
до того, как до него доходит `unlink()`, и уборка молча не срабатывает. Поэтому
`Backup::create()` перед каждой новой копией подчищает всё зависшее старше часа
сама (`Backup::purgeTemp()`), и то же самое раз в цикл обслуживания делает
воркер — ноль зависших файлов это не гарантирует, но расти бесконечно им не даёт.

## По расписанию

Копия делается каждый день, если задано время:

```dotenv
BACKUP_SCHEDULE=03:30    # пусто — не делать
BACKUP_KEEP=7            # сколько копий держать
```

Расписание ведёт воркер, поэтому cron не нужен. Задача ставится в очередь
(`BackupJob`), чтобы долгий дамп не занимал круг расписания. Если копия не
сделалась и попытки кончились, всем, у кого есть право `system.manage`, уходит
уведомление — в ленту и письмом: остаться без копий молча хуже всего.

После новой копии лишние удаляются, остаются `BACKUP_KEEP` последних.

## Восстановление

Вещь крайняя: текущие данные заменяются целиком.

```bash
php bin/proton backup:restore proton-2026-09-13-031500-a7Kd-sqlite.sqlite.gz --force
```

Что происходит по порядку: копия проверяется; делается страховочная копия того,
что есть сейчас (её имя команда печатает — будет куда вернуться, если
восстановили не то); данные заменяются; в лог идёт запись уровня warning.

Без `--force` команда только покажет, что внутри копии, и остановится. Копию с
другой СУБД не примет: дамп MySQL в SQLite не вливается.

После восстановления воркер нужно перезапустить — `php bin/proton worker:restart`.

## Что стоит знать

- Каталог `var/backups` лежит вне `public`, и файл отдаёт код — копия базы не
  должна быть доступна по прямой ссылке.
- Имя файла проверяется: `..` и пути в нём не принимаются, иначе из панели можно
  было бы прочитать или удалить что угодно.
- Копии — это не архив на века: держите `BACKUP_KEEP` небольшим, а сами файлы
  забирайте с машины наружу (тем же `scp` по расписанию). Диск, на котором лежит
  база, и диск с копиями в идеале разные.
- Страница состояния (`php bin/proton status`) предупредит, если копий нет вовсе
  или свежей нет больше двух дней.

Тесты — `tests/BackupTest.php`: гоняются на отдельной базе-файле и в своём каталоге,
поэтому боевые данные и копии не трогают.
