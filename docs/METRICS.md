# Отчёты, показатели и присмотр

Три разные вещи, которые легко перепутать: **отчёты** — что происходило за период,
**показатели** — как сейчас работает приложение, **присмотр** — кто сообщит, когда
показатели уехали.

## Отчёты

Раздел **Отчёты** (право `system.view`) показывает ряды по периодам: регистрации,
входы, заметки, посылки вебхуков. Считает база, страница рисует столбики и отдаёт
тот же ряд файлом.

Свой отчёт — строка в `ReportsController::sources()`: запрос, колонка времени
и подпись. Выгрузка, периоды и график общие.

```php
'orders' => [
    'label'  => 'Заказы',
    'column' => 'created_at',
    'query'  => static fn () => Order::query()->where('paid', 1),
],
```

Ряд можно взять и напрямую:

```php
Reports::series(Order::query(), 'created_at', '2026-09-01', '2026-09-30');       // по дням
Reports::series(Order::query(), 'created_at', $from, $to, Reports::WEEK);        // по неделям
Reports::breakdown(Order::query(), 'status');                                    // разбивка
```

Периоды без записей приходят нулями — иначе график врёт, а в выгрузке пропадают
пустые сутки. Неделя обозначается датой понедельника: номера недель у SQLite,
MySQL и PHP считаются по-разному и на стыке годов разъезжаются.

## Показатели

`Support\Metrics` считает две разные вещи.

Счётчики запросов ведёт ядро: время ответа, коды 5xx, медленные ответы
(`METRICS_SLOW_MS`). Живут они в кэше почасовыми ведёрками, 25 часов. Своей
таблицы под них нет нарочно — запись в базу на каждый запрос стоит дороже, чем
стоят сами цифры. Очистка кэша их обнуляет, и это нормально.

```php
Metrics::requests(24);   // ['requests' => …, 'average_ms' => …, 'errors' => …, 'slow' => …]
```

Снимок состояния считается из базы и не зависит от того, работал ли сбор:

```php
Metrics::snapshot();     // пользователи, очередь, вебхуки, журнал, место на диске
```

Снимком отвечает `GET /api/v1/metrics` — ключ API плюс право `system.view`
у владельца ключа. Для внешнего мониторинга этого хватает; `/health` остаётся
без ключа — только то, что не жалко показать кому угодно.

`/health` не сваливает всё в одно «жив/не жив»: каждая зависимость — своё поле
в `checks` (`ok`, `warn` или `fail`), а `status` наверху — худшее из них, для
тех, кому нужен только код ответа.

```json
{
    "status": "ok",
    "app": "Proton",
    "checks": {
        "database": {"status": "ok", "ms": 1.2},
        "disk":     {"status": "ok", "free_mb": 102400},
        "queue":    {"status": "ok", "queued": 0, "failed": 0}
    },
    "time": "2026-09-16T12:00:00+00:00"
}
```

Порог диска общий с присмотром — `MONITOR_FREE_BYTES`, здоровье и присмотр не
должны спорить, что считать «мало места». Код ответа — 503 при `fail`, иначе 200
(`warn` не роняет ответ: мониторинг видит предупреждение, а не ложную тревогу).

Сбор выключается `METRICS_ENABLED=false`.

## Присмотр

`Support\Monitor` сравнивает показатели с порогами и уведомляет тех, у кого право
`system.manage` (лента плюс письмо). Зовёт его расписание, то есть воркер, раз
в `MONITOR_INTERVAL` секунд.

Пороги:

| Настройка | Что значит | По умолчанию |
|---|---|---|
| `MONITOR_FAILED_JOBS` | задач с ошибкой в очереди | 10 |
| `MONITOR_QUEUE_BACKLOG` | задач ждёт разбора | 500 |
| `MONITOR_ERRORS` | ошибок 5xx за час | 20 |
| `MONITOR_FREE_BYTES` | осталось места на диске | 500 МБ |

Про одну и ту же беду сообщается не чаще раза в `MONITOR_REPEAT_MINUTES` (60):
кончающийся диск не должен превращаться в сотню писем. Отметки лежат в `settings`
под ключами `monitor:alert:*` — сбросив такую, получите сообщение сразу.

Порог, о котором не хочется знать, отключается большим числом; весь присмотр —
`MONITOR_ENABLED=false`. Проверить, что видит присмотр прямо сейчас, можно и
без уведомлений: `Monitor::check(false)` возвращает найденные проблемы.
