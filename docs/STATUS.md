  подмена ничего не сдвигает; `User::hasAvatar()` проверяет не только запись
  в базе, но и что файл правда на диске — битая ссылка (потёрли в обход
  загрузки) не рисуется у всех сломанной картинкой; отдаётся с
  `Cache-Control: immutable` на год — адрес несёт хеш пути файла, поэтому
  замена фото меняет и ссылку, а без этого заголовка браузер перекачивал бы
  ту же картинку на каждой странице заново;
- баг: `Storage::put()` определял MIME уже после `move_uploaded_file()` — файла
  по старому пути к этому моменту нет, и тип всегда падал в
  `application/octet-stream`, независимо от настоящего содержимого. Задевало
  все загрузки, не только аватар (вложения к заметкам туда же), просто там
  подгрузка проверяет и расширение, поэтому не так бросалось в глаза. Тип
  теперь смотрят до переноса файла;
- `User::permissions()` считает права своей роли один раз за объект, а не на
  каждую проверку `View::can()` — пунктов меню в шапке больше десятка, и без
  кэша это был поход в `roles` на каждый; на удалённой базе разница на
  странице профиля — секунды, не миллисекунды (нашёл пользователь по живой
  жалобе «долго грузится», профилировщик показал 17 одинаковых `SELECT`);
  заодно `Connection::hasTable()` кэшируется на время запроса, со сбросом
  после любого DDL через `Schema\Builder`;
- документация: девятнадцать файлов в `docs/` плюс README и `CLAUDE.md`.

## Что сделано последним заходом

Ещё раунд Laravel-идей плюс CI: защита расписания от наложения, `cursor()`,
`HttpClient::fake()`, workflow для gitea и github.

1. **Защита расписания от наложения.** `Scheduler::run()` теперь берёт ту же
   `Database\Lock`, что и `runNow()` (`schedule:<имя>`), прежде чем выполнить
   задачу — если её уже держит другой процесс (второй воркер, или воркер и
   кнопка «Выполнить, что пора» разом), свой прогон просто пропускает задачу
   вместо того, чтобы выполнить её ещё раз. Тест — `tests/QueueTest.php`:
   задача под чужой блокировкой не выполняется, после освобождения — как
   обычно.
2. **`cursor()` у построителя и моделей.** `Note::query()->cursor()` — модели
   по одной, без порций в памяти; `$db->table(...)->cursor()` — то же для
   сырых строк. В MySQL — по-настоящему без буферизации
   (`PDO::MYSQL_ATTR_USE_BUFFERED_QUERY => false`), а не просто `fetch()` в
   цикле, который сам по себе экономии не даёт: mysqlnd и так грузит всё в
   память при выполнении запроса, если буферизацию явно не выключить.
   Заодно в `docs/DATABASE.md` вымышленный `Order` заменён реальным `Note`.
   Тесты — `tests/DatabaseTest.php` (сырой cursor) и `tests/ModelTest.php`
   (модели по одной).
3. **`HttpClient::fake()`.** Подмена чужого HTTP-сервиса без своего
   класса-наследника на каждый случай (наследование, как у `WebhookTestClient`
   в `tests/WebhookTest.php`, остаётся — когда нужно не готовый ответ, а
   проверить логику самого клиента). Заодно — первый тест для
   `MailerServiceDriver`: раньше его нечем было проверить без похода в
   реальный почтовый сервис, теперь `tests/MailTest.php` гоняет и успешную
   отправку, и ответ с ошибкой, проверяя ровно то, что улетело (адрес,
   заголовок авторизации, тело). Плюс `tests/HttpClientTest.php` на саму
   механику подмены.
4. **CI для gitea и github.** `.github/workflows/tests.yml` и
   `.gitea/workflows/tests.yml` — `php bin/proton test` на каждый push в
   `main` и pull request, без `.env` (тесты и так не читают боевые настройки).
   Два прогона на SQLite (PHP 8.1 и 8.3) и один на настоящем MySQL в
   контейнере — раз проект держит оба диалекта одним кодом, CI должен
   проверять оба, а не только тот, что на машине разработчика. Файлы
   независимы: GitHub ставит PHP экшеном `shivammathur/setup-php`, Gitea —
   через `docker-php-ext-install` внутри контейнера `php:<версия>-cli`,
   потому что раннер Gitea не обязан уметь тянуть экшены с github.com.
   Живая проверка (MySQL-путь тестов) сделана только за счёт чтения кода —
   раннер настоящей учётной записи `proton` на боевом MySQL не имеет прав
   создавать новые базы, а поднимать локально Docker ради проверки не стал;
   первый реальный прогон будет виден после push по бейджам в README.

## Предыдущий заход

Ещё один раунд Laravel-идей: наблюдатели моделей, режим обслуживания, cron
в расписании, скоуп у API-токенов, цепочка задач.

1. **Наблюдатели моделей.** `Database\Model\Observers` — реестр
   `config/observers.php`, методы с именами событий (`saving`, `created`,
   `deleted` и т.д.) вызываются из тех же мест, что и `Events::fire('model.*')`,
   вызовом через `method_exists` — писать заглушки на неиспользуемые события
   не нужно. Живой пример — `App\Observers\NoteObserver`: он же вскрыл реальный
   баг. `forceDelete()` заметки из корзины не трогал её вложения
   (`Files\Attachment`) — ни строку в базе, ни файл, и `files:orphans` такой
   файл сиротой не считает (запись в `attachments` на него по-прежнему есть).
   Наблюдатель на `deleted($model, $force)` зовёт `Attachment::detachAll()`,
   когда `$force === true`. Тесты — `tests/ObserversTest.php` (реестр и
   отмена через «до»-методы) и новый тест в `tests/FilesTest.php` (реальный
   сценарий с вложением).
2. **Режим обслуживания.** `Support\Maintenance` — флаг-файл
   (`var/maintenance.json`, не запись в базе: база в момент наката сама может
   быть недоступна). `php bin/proton down --message="…" --allow=IP,IP
   --retry=60` / `up`, и та же пара кнопок в панели — **Состояние →
   Обслуживание** (сообщение вводится прямо в форме). Пока флаг стоит, любой
   запрос до роутера получает 503 (JSON — API, страница — браузеру) с
   `Retry-After`, если задан `--retry`. Правом `system.manage` режим не
   ограничивает: администратору не нужно вписывать себя в allow-список ради
   собственной же правки. Проверено вживую в браузере — форма включения,
   бейдж состояния и кнопка выключения работают через настоящий локальный
   `php bin/proton serve`, не только автотестами. Тесты — `tests/MaintenanceTest.php`
   (флаг, допуск по IP, обход по system.manage, JSON-ответ API).
3. **Cron-выражения в расписании.** `Scheduler::cron('*/15 9-18 * * 1-5', 'имя',
   $колбэк)` — пять полей, как в обычном cron (без имён месяцев/дней недели),
   свой разбор в `Support\CronExpression` — числа, `*`, списки, диапазоны,
   шаг `/n`. Негодное выражение роняет регистрацию сразу, при загрузке
   `config/schedule.php`, а не «молча никогда не наступит». Задача по cron
   засчитывается не чаще раза в минуту, даже если `run()` зовут чаще. Пример —
   третья демонстрационная задача в `config/schedule.php`
   (`demo:cron-heartbeat`), рядом с `demo:heartbeat`. Заодно поправлены
   `docs/QUEUE.md` — там `everyAfterPrevious()`/`dailyAt()` были
   проиллюстрированы вымышленными `DailyReport`/`Reindex`, заменены на
   реальные `demo:heartbeat`/`notes:rebuild-slugs` из `config/schedule.php`.
   Тесты — `tests/CronExpressionTest.php` (разбор выражения) и
   `tests/QueueExtraTest.php` (регистрация, гейт раз в минуту, ошибка на
   негодном выражении).

   Заодно, гоняя полный набор тестов с `--shuffle` (сам решил перестраховаться
   раз работаю с расписанием), поймал не связанную с cron утечку: `tests/
   MetricsTest.php` гасил `monitor:alert:http.errors` в `'0'`, но не убирал
   саму строку — она изредка ловилась LIKE-проверкой в `tests/DatabaseTest.php`
   на общей базе при определённом порядке тестов. Заменено на `Setting::forget()`.
   Порядково-зависимых утечек в `tests/HttpTest.php` (подписки на события,
   счётчик настроек) `--shuffle` тоже находит — они старше сегодняшних правок
   и в план этого захода не входили, оставлены как есть.
4. **Скоуп у API-токенов.** Ключ теперь может нести список прав, которыми
   ограничен, даже если у владельца их больше: `ApiToken::issue($name, $userId,
   $ips, $days, 'notes.view,notes.manage')` (миграция `add_token_abilities`,
   колонка `abilities`), консоль — `key:create ... --abilities=`, панель —
   поле «Права ключа» в **Ключи API**. Пусто — как раньше, ключ может всё,
   что может владелец. Схема — `Viewer::forToken(User, ApiToken)`: считает
   `array_intersect()` прав владельца и списка ключа один раз при сборке
   Viewer, дальше `can()`/`canAny()`/`scope()` работают как обычно и знать
   про токены не должны. Ключ не может получить то, чего нет у самого
   владельца, — скоуп только урезает, роль остаётся источником правды.
   Тест — `tests/HttpTest.php`: ключ админа со скоупом `notes.view` не проходит
   там, где нужен `system.view` (хотя у самого админа оно есть), и наоборот —
   скоуп с чужим правом ничего не даёт, если его нет у владельца. Проверено и
   вживую через панель (реальный POST с CSRF, не только автотестом) —
   выпущенный ключ показывает скоуп в списке.
5. **Цепочка задач.** `Queue::chain([[КлассА, payload], [КлассБ, payload], ...])` —
   следующий шаг встаёт в очередь только после успеха предыдущего; упавшая
   насовсем задача останавливает цепочку сама, без проверок в вызывающем коде.
   Данные, которых не существовало до выполнения шага (сгенерированное имя
   файла), следующий шаг получает через `$this->carryToNext([...])` внутри
   `handle()`, а не через payload — заранее их и не бывает. Реализация:
   служебный ключ `__chain` в payload задачи, `Worker::perform()` зовёт
   `Queue::continueChain()` сразу после `Queue::complete()`.

   Пример — настоящий, не придуманный: фоновая выгрузка большого списка
   (`Controller::exportCsv()`) раньше сама слала уведомление внутри
   `ExportJob::handle()` — теперь это второй шаг цепочки, `NotifyExportReadyJob`.
   Сорвавшееся письмо больше не заставляет пересобирать файл повторной
   попыткой всей выгрузки. Существующий тест `tests/ImportExportTest.php`
   («выгрузка: слишком большая выборка уходит в очередь») прошёл без единой
   правки — он уже гонял настоящий `Worker`, а не звал `handle()` напрямую.
   Плюс новые `tests/QueueChainTest.php` (передача данных, остановка на
   мёртвой задаче, пустая цепочка) и живая проверка на боевой базе через
   `tinker`-скрипт (не автотест) — от постановки в очередь до письма и назад,
   с уборкой созданной записи и файла.

## Заход раньше

Ревизия архитектуры и мусора по всему проекту, с починкой того, что нашлось:

1. **Пример контейнера.** `config/services.php` был пуст, а `docs/CONTAINER.md`
   иллюстрировал привязки вымышленными классами (`App\Contracts\Storage` и
   соседи), которых нет в коде — прямое нарушение правила «пример настоящий,
   а не выдуманный». Добавлен живой пример: `App\Contracts\NoteLimiter` →
   `App\Services\ConfigNoteLimiter`, лимит заметок на пользователя вынесен из
   `NotesController::store()` в привязку. Заодно поправлены `docs/WEBHOOKS.md`
   (вымышленный `MarkOrderPaidJob` → реальный `RebuildNoteSlugsJob`) и
   опечатка в примере имени файла в `docs/MIGRATIONS.md`.
2. **Накат миграций из панели.** Кнопка «Применить миграции (N)» в
   **Состояние → Обслуживание**, показывается только когда есть что катить.
   Тот же `Migrator::run()` и та же блокировка, что у консольной команды.
3. **Баг: размер базы в показателях.** `Metrics::storage()` всегда читал файл
   `var/app.sqlite`, даже когда `DB_DRIVER=mysql` — на боевой конфигурации
   показывал 0 или случайный старый файл. Теперь для MySQL считает
   `SUM(data_length + index_length)` по `information_schema.tables`. Нашёл
   пользователь, глядя на панель состояния.
4. **Утечка временных файлов при проверке копий.** В `var/tmp` накопилось
   больше 300 файлов `backup-check-*.sqlite` — `Backup::verifySqlite()` их
   создаёт при каждой проверке и убирает `@unlink()` в `finally`, но на
   Windows это иногда молча не срабатывает (PDO не всегда сразу отпускает
   файл). Добавлен `Backup::purgeTemp()`: подчищает всё зависшее старше часа,
   зовётся и в начале `Backup::create()`, и воркером в общей уборке — по
   тому же принципу, что `ExportFile::purge()` и соседи.
5. **Мусор в дереве проекта.** Убраны: `.gigacode/` из корня (след другого
   ИИ-инструмента, не был в `.gitignore` — добавлен), десяток пустых
   каталогов-обломков более раннего рефакторинга (`framework/Http/Controllers/*`,
   `framework/View/views/{admin,auth,install,mail}`,
   `resources/views/{errors,layouts}` и другие — не в git, просто засоряли
   дерево в IDE), локальные `var/` объедки ручных проверок (старые CSV
   выгрузки, тестовые файлы). Заодно нашёлся и починен баг помельче:
   `tests/MakeCrudTest.php::cleanupCrud()` удалял файлы генератора, но не
   каталог вьюх под ними — каждый прогон `php bin/proton test` оставлял три
   пустых `resources/views/zz_crud_*`.
6. **Отправка копий базы на FTP.** Свой клиент на потоках (`Backup\Ftp`) —
   ни composer, ни расширение `ftp`, только `stream_socket_client`, как у
   SMTP-клиента почты. Пассивный режим, каталог на сервере заводит сам
   (`MKD`), если его нет. Подключена к расписанию: если задан `FTP_HOST`,
   после каждой плановой копии `BackupJob` ставит `ShipBackupJob` в очередь —
   сеть до чужого сервера не держит готовый дамп. Плюс ручная отправка
   (`backup:ship <файл>`, кнопка в панели). Настоящего FTP-сервера в проекте
   ещё нет, поэтому клиент проверен против игрушечного однопроходного сервера
   (`tests/support/fake_ftp_server.php`, поднимается `proc_open` прямо в
   тесте) — разбор PASV, отправка данных и коды ошибок настоящие, не
   угаданные. Живая проверка тоже прошла: пользователь поднял Pure-FTPd на
   домашнем сервере (`10.10.10.1`), `backup:ship` доставил копию, размер на
   сервере совпал с локальным байт в байт (проверено отдельным `LIST` по
   тому же протоколу). Учётные данные легли в боевой `.env` этой машины.
7. **Второй пример расписания.** `config/schedule.php` дополнен
   `everyAfterPrevious()`-примером (был только `dailyAt()`) — пересчёт slug
   всех заметок, выключен по умолчанию (`NOTES_SLUG_RESYNC`): выяснилось на
   ходу, что задача без такого выключателя пушит задачу в очередь при любом
   прогоне `Scheduler::run()`, включая внутри тестов на общей базе — сломала
   два несвязанных теста, ждавших пустую очередь. Урок: пример в
   `config/schedule.php`, в отличие от `demo:heartbeat`, не должен молча
   менять общее состояние (очередь) без явного включения.

Всё уже применённое перед коммитом прогнано полным набором тестов
(`php bin/proton test`) — без ошибок.

## Дальше по плану

Волны генератора разделов, вебхуков и уведомлений, настроек и копий базы,
фильтров и сортировки, импорта-экспорта и отчётов, показателей и присмотра,
корзины и вложений, комментариев и переноса окружений, а из последнего
брейншторма — tinker, модельные события, кэш запроса, вход под пользователем,
отладочная панель — закрыты. Что обсуждалось, но не решено:

- приоритетные очереди с квотой воркера — нужно сперва решить, как считать
  квоту (по числу задач подряд или по доле времени воркера), отложено;
- сохранённые наборы фильтров («мои непрочитанные», «заказы за месяц») со ссылкой,
  которой можно поделиться;
- двухфакторный вход (TOTP) — код для этого писать самим, внешних библиотек нет;
- `UsersController::roles()` читает роль отдельным запросом на каждого
  пользователя списка (нашла отладочная панель) — мелкая правка, не срочная;
- из брейншторма «что ещё сделать» (крон-задачи и не только), не начато:
  канал уведомлений в Telegram/Slack, проверка TLS-сертификата на истечение
  по расписанию, внешний heartbeat (dead man's switch), дайджест на почту
  из `Support\Reports`, полнотекстовый поиск (FTS5/FULLTEXT одним фасадом,
  как `hasTable`/`hasColumn`), последние ошибки из логов на панели
  «Состояние», проверка целостности данных по расписанию (осиротевшие связи).

Проход «примеры и комментарии» по всем расширяемым местам фреймворка (events,
commands, notifications, webhooks, incoming, settings, exports, trash,
widgets, policies, schedule, services) теперь закрыт полностью — стало
привычкой сопровождать новое сразу, а не отдельным заходом (см. правило в
CLAUDE.md/памяти).

## О чём помнить

- База теперь общая MySQL для дева и прода (раньше `var/app.sqlite` шарился
  копированием файла) — `DB_DRIVER=mysql` в `.env`. Явных запретов писать в неё
  во время разработки нет, проект ещё в разработке, но это боевая база: см.
  «Работа с данными» в `CLAUDE.md` — ничего лишнего не заводить, а что завёл
  для проверки — убирать точно по id.
- На сервере `.env` живёт своей жизнью и в деплой не попадает — 16 сентября там
  нашёлся `APP_ENV=local` вместо `production` (см. `docs/PROD_CHECK.md`): из-за
  этого выключена защита `migrate:fresh` от запуска на боевой базе. Стоит поправить
  вручную на сервере.
- Проверка прода curl’ом, браузером и нагрузкой — `docs/PROD_CHECK.md`. Разовый
  снимок на дату, не чек-лист на каждый раз.
- База считается боевой: ничего не удаляем и не затираем по своей инициативе. После
  проверок свои записи убираем точечно, по id.
- Тесты всегда идут на своей базе (`TEST_DB_*`), настройки `DB_*` раннер не читает.
- После выкладки кода воркер нужно перезапускать — он держит классы в памяти.
- Копии базы лежат в `var/backups` и в git не попадают. Перед рискованной правкой
  схемы стоит сделать `backup:create`.
- Обращения к чужим сервисам — только через `Support\HttpClient`, своих `curl_init`
  в коде быть не должно.
- Правила проекта, архитектура и соглашения — в `CLAUDE.md` в корне.
