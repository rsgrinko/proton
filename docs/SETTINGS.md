# Настройки из панели

`.env` задаёт то, без чего приложение не поднимется: база, ключ, адрес. Всё
остальное — название, открыта ли регистрация, чем отправлять письма, сколько
записей на странице — админ меняет в панели, раздел **Настройки** (право
`settings.manage`).

Значение из базы ложится поверх `.env`. Пока настройку не трогали, работает то, что
в файле.

## Своя настройка

Какие настройки есть — решает код, как с правами и событиями вебхуков. В базе
лежат только значения. Свои объявляются в `config/settings.php`:

```php
use Rsgrinko\Proton\Support\Settings;

Settings::register('shop.currency', 'Валюта', Settings::STRING, 'Магазин');
Settings::register('shop.min_order', 'Минимальный заказ', Settings::INT, 'Магазин', [], '0 — без ограничения');
Settings::register('shop.mode', 'Режим', Settings::SELECT, 'Магазин', [
    'retail' => 'розница',
    'wholesale' => 'опт',
]);
```

Читается как обычная конфигурация — место чтения не знает, откуда взялось значение:

```php
$currency = Config::get('shop.currency');
```

Значение по умолчанию стоит положить в `config/config.php` рядом с остальными, тогда
у настройки есть осмысленное состояние «не трогали»:

```php
'shop' => [
    'currency'  => Env::string('SHOP_CURRENCY', 'RUB'),
    'min_order' => Env::int('SHOP_MIN_ORDER', 0),
],
```

Типы: `STRING`, `TEXT` (многострочное поле), `INT`, `BOOL` (галочка), `SELECT`
(список вариантов), `SECRET` (поле-пароль, значение шифруется `Crypto` и в журнал не
попадает).

## Как это работает

Значения лежат в таблице `settings` под префиксом `config:` — рядом с
рантаймовыми отметками ядра вроде `worker:restart`, но не смешиваясь с ними.

Накладываются они один раз за процесс: `Settings::apply()` зовут ядро (на каждый
запрос) и консоль (перед командой). База недоступна — приложение просто работает на
`.env`, в лог уходит предупреждение.

Воркеру правка настроек достанется после перезапуска: он держит конфигурацию в
памяти, как и классы. То есть `worker:restart` нужен не только после выкладки кода.

## Сброс

Кнопка «Сбросить» удаляет значение из базы, а не записывает в неё то же, что в
`.env`. Разница существенная: иначе правка `.env` потом ничего бы не меняла —
в базе лежало бы старое значение и продолжало перекрывать файл.

Настройки, у которых значение взято из базы, помечены в панели как «изменено» и
собраны отдельным списком внизу страницы.

## Из кода

```php
Settings::value('ui.per_page');      // текущее значение: база, иначе .env
Settings::overridden('ui.per_page'); // задано ли в базе
Settings::put('ui.per_page', '50');  // записать и применить сразу
Settings::forget('ui.per_page');     // снова брать из .env
Settings::problem('ui.per_page', 'много'); // текст ошибки или пустая строка
```

`put()` принимает только ключи из реестра: записать в базу что попало и потом
удивляться, откуда в конфиге мусор, не получится.

## Чего здесь нет

Настроек базы (`db.*`) и ключа приложения (`app.key`). Их правка может оставить
приложение без доступа к данным или сделать нечитаемыми уже зашифрованные секреты —
это работа с `.env` и с сервером, а не кнопка в браузере. Всё остальное из
`config/config.php`, вплоть до отладки и адреса приложения, в реестре есть.

## Перенос между окружениями

Настройки, правленные из панели, и свои роли переносятся файлом — донастраивать
второе окружение руками через форму не нужно:

```bash
php bin/proton settings:export                    # var/export/settings-ГГГГММДД-ЧЧММСС.json
php bin/proton settings:export --out=deploy.json   # или в свой путь

php bin/proton settings:import deploy.json          # спросит подтверждение
php bin/proton settings:import deploy.json --force   # для скрипта деплоя
```

Секреты (тип `Settings::SECRET`, например ключ почтового сервиса) в файл не
попадают — они зашифрованы мастер-ключом исходного окружения (`APP_KEY`) и на
другом не расшифруются. Список пропущенных ключей команда печатает, значения
переносятся в целевой `.env` руками.

Встроенную роль администратора команда не выгружает и не правит — её права
всегда берутся из кода. Остальные роли ищутся по имени: совпало — обновляются
описание и права, нет — заводится новая. Настройка, которой целевой реестр не
знает (другая версия кода), пропускается с пометкой в выводе, а не роняет
остальной импорт. Ничего не удаляется: лишних на базе ролей файл не касается.

## Выгрузка в .env

Кнопка «Выгрузить .env» на странице настроек (`GET admin.settings.export-env`,
право `settings.manage`) отдаёт файлом не JSON, а сам `.env` — таким, каким он
был бы, если бы значения из панели вписали в файл руками. За основу берётся
действующий `.env` (или `.env.example`, если файла ещё нет): строки известных
переменных заменяются текущим эффективным значением, остальное — секреты базы,
ключ приложения, чужие переменные — остаётся как есть. Секреты (SMTP-пароль,
ключ почтового сервиса, пароль FTP) выгружаются расшифрованными: `.env` и так
лежит на сервере открытым текстом, иначе перенести их на другое окружение
было бы нечем. Каждая выгрузка попадает в журнал действий.

Так делают деплой на новое окружение: настроили всё в панели на одном сервере,
скачали `.env`, положили на другой — без сверки формы поле за полем.
