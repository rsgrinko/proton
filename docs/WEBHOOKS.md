# Вебхуки

Событие внутри приложения уходит наружу подписчику: посылка POST с JSON,
подписью и повторами. Отправляет её воркер, поэтому страница не ждёт чужой
сервер, а на каждую посылку остаётся строка в журнале доставок — с кодом ответа
и временем.

Механика собрана из готового: события даёт `Events`, доставку с повторами —
`Queue`, секрет подписки шифрует `Crypto`.

## Как это выглядит для подписчика

```
POST /hooks/proton HTTP/1.1
Content-Type: application/json
User-Agent: Proton-Webhook/1.0
X-Proton-Event: note.created
X-Proton-Delivery: 142
X-Proton-Timestamp: 1789248523
X-Proton-Signature: sha256=d17eb4a7df26140c84da555675a8ed5d…
X-Request-Id: 7167d8986f15ae47

{
  "event": "note.created",
  "timestamp": 1789248522,
  "sent_at": "2026-09-13 00:28:42",
  "app": "Proton",
  "data": {
    "note": { "id": 5, "title": "Проверка вебхуков", "user_id": 3 }
  }
}
```

Удачей считается ответ `2xx`. Всё остальное — повод повторить.

### Проверка подписи на стороне подписчика

Подписывается строка «время точка тело», ключ — секрет подписки:

```php
$expected = 'sha256=' . hash_hmac(
    'sha256',
    $_SERVER['HTTP_X_PROTON_TIMESTAMP'] . '.' . file_get_contents('php://input'),
    $secret
);

// hash_equals, а не ==: сравнение на время подсказывает подпись по байтам
if (!hash_equals($expected, $_SERVER['HTTP_X_PROTON_SIGNATURE'])) {
    http_response_code(403);

    return;
}

// Время внутри подписи — чтобы перехваченную посылку нельзя было повторить
// через сутки; расхождение больше пяти минут стоит отвергать
if (abs(time() - (int) $_SERVER['HTTP_X_PROTON_TIMESTAMP']) > 300) {
    http_response_code(403);

    return;
}
```

Повтор посылки приходит с тем же `X-Proton-Delivery`: подписчик должен
переживать дубль — по этому номеру он и узнаёт, что уже видел посылку.

## Подписки

Заводятся в панели: **Вебхуки** (право `webhooks.manage`). У подписки есть адрес,
набор событий, секрет и состояние.

- **События** отмечаются галочками. Отдельная галочка «Все события» берёт и те,
  что появятся позже.
- **Секрет** придумывается сам или задаётся руками. Его можно заменить —
  старый перестаёт подходить сразу. В базе секрет лежит зашифрованным
  (`Crypto`, мастер-ключ `APP_KEY`), а не хешем: им подписывается каждая
  посылка, значит читать его придётся снова.
- **Пробная посылка** — кнопка «Отправить пробную посылку» или команда
  `webhook:test`. Событие у неё `webhook.test`.
- Подписка, не ответившая `WEBHOOKS_DISABLE_AFTER` раз подряд, **отключается
  сама**: возить посылки в никуда незачем. Включение обратно обнуляет счётчик.
  Об этом узнают все, у кого есть право `webhooks.manage` — уведомлением в ленте
  и письмом (см. [NOTIFICATIONS.md](NOTIFICATIONS.md)): молча отключённая
  подписка означает тихо потерянные события.

```bash
php bin/proton webhook:list             # подписки и состояние посылок
php bin/proton webhook:list --events    # на что вообще можно подписаться
php bin/proton webhook:test 1           # отправить пробную посылку сразу
php bin/proton webhook:test 1 --queue   # только поставить в очередь
```

## Реестр событий

Подписаться можно только на событие из реестра — события живут в коде, как и
права, и миграция для них не нужна. Свои добавляются в `config/webhooks.php`:

```php
use Rsgrinko\Proton\Webhooks\Webhooks;

Webhooks::register('order.paid', 'Заказ оплачен', 'Заказы');
```

События ядра: `user.registered`, `user.login`, `user.logout` и служебное
`webhook.test`.

Дальше событие достаточно объявить — подписчикам оно уедет само, потому что
реестр повешен на шину событий строкой `Webhooks::subscribe()` в
`config/events.php`:

```php
Events::fire('order.paid', ['order' => $order]);
```

Можно и напрямую, не объявляя событие шине:

```php
Webhooks::dispatch('order.paid', ['order' => $order]);
```

Что попадает в `data`: модели отдаются массивом (скрытые поля в нём уже
вырезаны — пароли и секреты наружу не уходят), массивы — как есть, посторонние
объекты и ресурсы выбрасываются.

## Доставка и повторы

`Webhooks::dispatch()` пишет посылку в журнал и ставит `DeliverWebhookJob` в
очередь. Задача несёт только номер посылки, а тело берёт из журнала: повтор
отправляет ровно то же, что первая попытка, и подпись сходится.

Повторы — обычные повторы очереди: `WEBHOOKS_ATTEMPTS` попыток с растущей паузой
(30 с, минута, две, …). Когда попытки кончились, посылка помечается
недоставленной, а подписке добавляется неудача.

Посылки идут своей очередью `webhooks`, чтобы медленный подписчик не задерживал
письма. Воркер разбирает несколько очередей через запятую, и задача из очереди
слева берётся раньше:

```bash
php bin/proton worker --queue=default,webhooks
```

Без ключа `--queue` воркер берёт обе эти очереди сам. Если разделять не нужно,
достаточно оставить `WEBHOOKS_QUEUE` пустым — посылки пойдут общей очередью.

Журнал доставок подчищается вместе с остальной уборкой воркера: строки старше
`WEBHOOKS_KEEP_DAYS` удаляются.

## Настройки

```dotenv
WEBHOOKS_ENABLED=true          # выключатель на всё
WEBHOOKS_TIMEOUT=10            # сколько ждать ответа подписчика, секунд
WEBHOOKS_ATTEMPTS=5            # попыток на посылку
WEBHOOKS_DISABLE_AFTER=20      # неудач подряд до самоотключения (0 — никогда)
WEBHOOKS_KEEP_DAYS=14          # сколько держать журнал доставок
WEBHOOKS_QUEUE=webhooks        # очередь для посылок (пусто — общая)
```

Обращения к чужим сервисам идут через `Support\HttpClient` — им же отправляет
драйвер почты `mailer`. Проверку сертификата он не отключает, и там, где у PHP
нет своего хранилища корневых сертификатов (обычное дело на Windows), путь
к набору задаётся настройкой:

```dotenv
HTTP_CA_BUNDLE=C:/path/to/cacert.pem   # взять: https://curl.se/ca/cacert.pem
HTTP_VERIFY_PEER=true                  # выключать не надо: ключи интеграций уйдут посреднику
```

## Таблицы

`webhooks` — подписки: адрес, события JSON-строкой, шифрованный секрет, флаг
активности, счётчик неудач подряд и отметки последней посылки.

`webhook_deliveries` — журнал: событие, тело посылки целиком, состояние
(`pending` | `sent` | `failed`), число попыток, код и обрезанный ответ
подписчика, время ответа в миллисекундах.

## Входящие вебхуки

Обратная сторона: чужая система стучится к нам. Адрес — `/api/v1/hooks/{ключ}`,
метод POST или GET, ключ API не нужен: отправитель его не знает.

Источник объявляется в `config/incoming.php`:

```php
Incoming::register('billing', 'Биллинг', 'BILLING_HOOK_TOKEN', static function (array $payload): void {
    if ((string) ($payload['event'] ?? '') !== 'order.paid') {
        return;
    }

    Queue::push(MarkOrderPaidJob::class, ['order' => (int) $payload['id']]);
});
```

Третий аргумент — **имя переменной**, а не сам токен: значение кладут в `.env`,
секрету в репозитории не место. Пустое имя означает «принимать без проверки» —
так подключают системы, которые не умеют слать ни заголовков, ни параметров.
А вот объявленная, но пустая переменная не пускает никого: это недонастройка, и
в журнале так и написано — «источник не настроен: переменная … пуста».

Токен ищется в трёх местах подряд, как умеет отправитель:

```
X-Proton-Token: <токен>
Authorization: Bearer <токен>
?token=<токен>          # или то же поле в теле
```

Значение берётся через `Env`, то есть и из окружения процесса, и из `.env`.
В журнал токен не попадает: параметр `token` из тела вырезается перед записью.

```
curl -X POST https://example.com/api/v1/hooks/billing \
     -H 'Content-Type: application/json' \
     -H 'X-Proton-Token: секрет' \
     -d '{"event": "order.paid", "id": 10231, "amount": 4500.00}'

curl "https://example.com/api/v1/hooks/billing?event=order.paid&id=10231&token=секрет"
```

У GET тела нет — параметры адреса и есть тело, обработчик в обоих случаях
получает одинаковый массив. Токен в адресе оседает в логах прокси, поэтому
заголовок надёжнее.

Обработчик должен отвечать быстро: отправитель ждёт ответа и повторит посылку,
если мы задумаемся, — всё долгое уходит в очередь. Упавший обработчик приём не
роняет: посылка помечается и отправителю уходит 202, чтобы он не слал её по
кругу.

Ответы: `200` — приняли и обработали, `202` — приняли, обработчик упал,
`401` — токен не подошёл, `404` — источника нет.

Каждая посылка попадает в `incoming_hooks` и видна на `/admin/webhooks/incoming`
вместе с телом запроса: без журнала разбираться с «мы отправили, а вы не
приняли» нечем.

## Что проверено тестами

`tests/WebhookTest.php`: реестр и фильтр событий, выбор подписок под событие,
шифрование секрета и сходимость подписи, состав посылки (включая то, что
посторонние объекты в неё не попадают), доставка, повтор после чужой ошибки,
самоотключение молчащей подписки, уборка журнала. В сеть тесты не ходят —
HTTP-клиент подменяется наследником.

`tests/HttpTest.php` проходит раздел панели настоящими запросами: форма заводит
подписку с секретом, пробная посылка встаёт в очередь, чужое событие посылок не
создаёт, удаление подписки уносит её журнал.

`tests/QueueExtraTest.php` — входящие: без токена не пускают, с токеном (и
заголовком, и параметром у GET) принимают, чужой токен отбивается, токен
читается из `.env`, а не только из окружения, недонастроенный источник никого
не пускает и говорит об этом в журнале, упавший обработчик приём не роняет,
токен в журнале не оседает.
