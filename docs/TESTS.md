# Тесты

Свой раннер, без PHPUnit и без composer: тест — это функция `test()`, проверки —
`assertSame()` и соседи.

```bash
php bin/proton test                     # весь набор
php bin/proton test --filter=queue      # по имени теста или файла
php bin/proton test --stop-on-failure   # остановиться на первой ошибке
php bin/proton test --shuffle           # перемешать порядок
php bin/proton test --shuffle=1234      # повторить тот же порядок по seed
php bin/proton test --slow=200          # с какого времени тест считается медленным
```

`--shuffle` ловит тесты, которые держатся на соседях: seed печатается, и упавший
порядок повторяется один в один.

## База всегда своя

Настройки `DB_*` из `.env` раннер **не читает вовсе** — по умолчанию это SQLite
в памяти. Тесты заводят и удаляют записи целыми таблицами, и боевой базе тут делать
нечего.

MySQL включается только переменными `TEST_DB_*`:

```env
TEST_DB_DRIVER=mysql
TEST_DB_DATABASE=proton_tests
TEST_DB_USERNAME=proton
TEST_DB_PASSWORD=…
```

Раннер не стартует, если имя тестовой базы совпало с боевой из `.env`. Перед прогоном
таблицы тестовой базы сносятся и схема накатывается заново.

Своё у прогона не только подключение: логи идут в `var/log/tests`, кэш и хранилище
файлов — в `var/tmp/*-tests`, почта — драйвер `null`. Новая проверка, которая пишет
на диск, кладёт своё туда же.

## Как выглядит тест

```php
test('очередь: упавшая задача возвращается с паузой', function (): void {
    $id = Queue::push(DemoJob::class, ['x' => 1]);

    $row = Queue::claim();
    assertNotNull($row);

    Queue::fail($row, 'сервер недоступен', 60);

    $again = Queue::claim();
    assertNull($again, 'до конца паузы задача браться не должна');
});
```

Файл кладётся в `tests/`, имя — `ЧтоТоTest.php`; заготовку делает
`php bin/proton make:test Orders`. Раннер подхватывает файлы сам, реестра нет.

## Проверки

| Проверка | О чём |
|----------|-------|
| `assertTrue`, `assertFalse` | условие |
| `assertSame($ожидалось, $получилось)` | строгое равенство |
| `assertNull`, `assertNotNull` | значение есть или его нет (`assertNotNull` возвращает значение) |
| `assertCount($сколько, $массив)` | размер |
| `assertContains`, `assertNotContains` | подстрока |
| `assertMatches($регулярка, $строка)` | по образцу |
| `assertStatus($код, $response)` | код ответа HTTP |
| `assertThrows(fn () => …)` | исключение (возвращает его — можно проверить текст) |
| `skipTest('почему')` | тест не выполним в этом окружении, это не ошибка |

Предупреждения PHP приравнены к ошибке: «Undefined array key» во вьюхе роняет тест,
а не уезжает в вывод.

## Помощники

**`afterTests(fn)`** — уборка после всего прогона, даже если тест упал. Отдельным
тестом уборку писать нельзя: с `--shuffle` она уедет в середину и унесёт чужие данные.

**`withConfig([...], fn)`** — настройки на время теста, возвращаются в любом случае:

```php
withConfig(['auth.registration' => false], static function (): void {
    assertStatus(404, (new Kernel())->handle(Request::create('GET', '/register')));
});
```

Настройки общие на весь прогон — менять их мимо `withConfig()` значит ломать соседей.

**`withOwnDatabase(fn)`** — своя чистая база со схемой. Для тестов-хозяев: тех, кто
разгребает очередь до дна или сносит всех пользователей. На общей базе такой тест
зависит от соседей и мешает им.

**`testDatabaseFile('имя')`** — база-файлом, когда её должен увидеть второй процесс
(воркер, сервер, блокировка).

**`HttpClient::fake([...])`** — чужой сервис отвечает заготовкой, в сеть никто не
ходит. Обязательно `HttpClient::reset()` после, иначе следующий тест тоже не пойдёт
в сеть:

```php
HttpClient::fake(['*/api/v1/messages' => ['status' => 500, 'body' => '{"error":"..."}']]);

try {
    // код, который где-то внутри делает (new HttpClient())->post(...)

    assertSame('POST', HttpClient::recorded()[0]['method']);
} finally {
    HttpClient::reset();
}
```

Своей маски адреса нет — подмена отвечает пустым 200: тесту, которому нужен код
ответа, придётся его задать явно, а не полагаться на «пришло же что-то». Когда
нужно не готовый ответ, а проверить логику самого клиента (разные коды подряд,
исключение на середине) — наследник `HttpClient`, как `WebhookTestClient`
в `tests/WebhookTest.php`.

## Что покрыто сейчас

`AuthTest` — вход, «запомнить меня», сеансы и права; `DatabaseTest` и `ModelTest` —
построитель запросов, модели и связи; `MigrationTest` — накат, откат и повторный
накат; `QueueTest` — очередь, повторы и расписание; `MailTest` — сборка
письма и драйверы; `RouterTest` — маршруты и прослойки; `ValidatorTest` — правила
проверки ввода; `SupportTest` — строки, кэш, события, счётчики, логи, файлы, адреса;
`HttpTest` — настоящие ядра: обход GET-маршрутов сайта, панели и API, установщик на
пустой базе.

`HttpTest` идёт на общей базе, поэтому за собой нужно прибирать: записи, оставленные
в таблицах, ломают соседние тесты.

## На что смотреть при отладке

- тест падает только в общем прогоне — виноват сосед: гоняйте `--shuffle` и смотрите
  seed, скорее всего не прибрана запись или подменена настройка;
- тест падает только на MySQL — обычно это диалект: повторённое имя параметра в
  запросе или `ALTER`, который SQLite прощает;
- тест «иногда» падает по времени — ищите зависимость от `time()` на границе секунды.

## CI

`.github/workflows/tests.yml` и `.gitea/workflows/tests.yml` гоняют `php bin/proton
test` на каждый push в `main` и на каждый pull request — тем же способом, что и
руками: своя база, `.env` не нужен вовсе. Два прогона на SQLite (PHP 8.1 и 8.3 —
минимальная объявленная версия и то, что реально стоит в разработке) и один на
настоящем MySQL в контейнере (`TEST_DB_DRIVER=mysql`) — иначе диалект-специфичный
баг всплывает только у того, кто разрабатывает на другой базе, чем прод.

Файлы почти одинаковые: GitHub гоняет job прямо на раннере через
`shivammathur/setup-php`, Gitea — внутри контейнера `php:<версия>-cli` с
`docker-php-ext-install`, потому что раннер Gitea не обязан уметь ставить
экшены с github.com. Меняя одну версию PHP или список расширений, второй файл
нужно поправить тем же самым — они не связаны и не подтягивают друг друга.
