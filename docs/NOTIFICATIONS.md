# Уведомления

Сказать человеку, что что-то случилось: строкой в его ленте внутри приложения и
письмом. Каналы выбирает само уведомление, адресата можно указать поимённо или
«всем, у кого есть право».

Уведомления — внутренняя сторона событий, вебхуки — внешняя: одно и то же
событие может и уехать подписчику посылкой, и лечь в ленту администратору.

## Своё уведомление

Класс-наследник `Notification`: что произошло, как это назвать и куда вести.

```php
use Rsgrinko\Proton\Http\Router;
use Rsgrinko\Proton\Notifications\Notification;
use Rsgrinko\Proton\Notifications\Notify;

final class OrderPaid extends Notification
{
    public function __construct(private Order $order)
    {
    }

    public function type(): string  { return 'order.paid'; }
    public function title(): string { return 'Заказ №' . $this->order->id() . ' оплачен'; }
    public function body(): string  { return 'Сумма: ' . $this->order->total . ' ₽'; }

    // Адрес с доменом: уведомление уходит и письмом, а там путь не кликается
    public function url(): string   { return Router::absolute('orders.show', ['id' => $this->order->id()]); }

    public function channels(): array { return [Notify::DATABASE, Notify::MAIL]; }
}
```

Обязателен только `title()`. Остальное имеет разумные значения: текст пустой,
ссылки нет, канал один — лента.

`type()` — короткий код, по которому уведомления отличают друг от друга, не
разбирая текст. Он виден в ленте и удобен для выборок.

Живой пример в приложении — `app/Notifications/NoteCreatedNotification.php`,
подписанный на `note.created` в `config/events.php`: связка «событие ->
уведомление» целиком, от объявления класса до подписки.

## Отправка

```php
Notify::send($user, new OrderPaid($order));                  // одному
Notify::sendMany($users, new OrderPaid($order));             // нескольким
Notify::toPermission(Permission::SYSTEM_MANAGE, $notification); // всем, у кого право
```

`toPermission()` избавляет от отдельного списка адресатов: «тем, кто отвечает за
сервис» — это просто «у кого есть право». Отключённые пользователи не получают
ничего. Кто попадёт в рассылку, можно спросить заранее — `Notify::whoCan($право)`.

`send()` возвращает каналы, которые действительно отработали. Уведомление никогда
не роняет то, что его вызвало: сорвавшийся канал пишется в лог
(`var/log/app-*.log`, метка `notifications`), остальные продолжают работать.

## Каналы

| Канал | Что делает |
|-------|------------|
| `Notify::DATABASE` | строка в ленте пользователя (таблица `notifications`) |
| `Notify::MAIL` | письмо через очередь — страница не ждёт чужой SMTP |

Письмо собирается общим шаблоном `resources/views/mail/notification.php`:
заголовок, текст, ссылка. Нужно своё — переопределите `mail()`:

```php
public function mail(User $user): Message
{
    return Message::to((string) $user->email)
        ->subject('Заказ оплачен')
        ->view('mail/order-paid', ['order' => $this->order, 'user' => $user]);
}
```

Канала `mail` нет смысла ждать там, где у пользователя нет адреса: письмо не
уйдёт (и в списке каналов его не будет), а лента сработает как обычно.

Неизвестное имя канала — ошибка, а не тишина: опечатка в `channels()` иначе
теряется вместе с уведомлением.

## Лента

Страница `/notifications` — своя у каждого вошедшего, права для неё не нужно:
фильтр по владельцу уходит в SQL, поэтому чужого уведомления для человека просто
не существует. Есть фильтр «только непрочитанные», чтение по одному, «прочитать
всё» и удаление.

Число непрочитанных показывает шапка (`UserNotification::unreadFor()` — один
`COUNT` на страницу, и только вошедшему).

Нажатие на уведомление со ссылкой отмечает его прочитанным и уводит по адресу —
то есть лента работает как список дел, а не как архив.

## Уведомления ядра

`WebhookDisabledNotification` — подписка на события отключилась сама, потому что
подписчик долго не отвечал. Уходит тем, у кого право `webhooks.manage`, и лентой,
и письмом: молча отключённая подписка означает тихо потерянные события.

## Настройки и уборка

```dotenv
NOTIFICATIONS_KEEP_DAYS=90   # сколько держать прочитанные уведомления
```

Прочитанные старше срока убирает воркер вместе с остальной уборкой
(`Notify::purge()`). Непрочитанные не удаляются вовсе — человек их ещё не видел.

## Таблица

`notifications`: владелец, тип, заголовок, текст, адрес перехода, время создания
и время прочтения (`read_at` пусто — непрочитано). Индексы — по владельцу с
`read_at` (лента и счётчик) и по дате (уборка).

Модель называется `UserNotification`, чтобы не путаться с самим уведомлением:
`Notifications\Notification` — описание «что случилось», `UserNotification` — его
след в ленте одного человека.

## Что проверено тестами

`tests/NotificationTest.php`: запись в ленту со всеми полями, письмо через очередь
(и что без годного адреса лента всё равно срабатывает), неизвестный канал,
счётчик непрочитанных и чтение (в том числе что повторное чтение не переписывает
время), адресация по праву с отключёнными и чужими ролями, уведомление об
отключённой подписке, уборка, не трогающая непрочитанные.

`tests/HttpTest.php`: лента отвечает, чужих уведомлений в ней нет, чтение ведёт по
ссылке уведомления, чужое уведомление — «не найдено», «прочитать всё» обнуляет
счётчик.

`tests/NoteCreatedNotificationTest.php`: пример из приложения — `note.created`
доводит уведомление до тех, у кого право `data.all`.
